# Repository Memory

## Stable Context
- **資料來源原則**  
  - 所有可追溯的事實與決策必須以 GitHub Issue 或 Comment 為唯一原始來源。  
  - `shared/manual.md` 只作為人類手動維護的長期記憶摘要，**不會**被自動覆寫。

- **記憶管理流程**  
  - `compact-memory workflow` 會在每次執行時讀取 `shared/manual.md`，但不會寫回或改寫此檔案。  
  - 每日快照 (`daily/*.json`) 只負責蒐集當前可見的 Issue，若無可用 Issue，則保留既有記憶不變。

- **Repo 共同慣例**  
  - **不複製完整 Issue 內容**：摘要或抽象化的資訊才會寫入長期記憶。  
  - **穩定規則與長期決策** 必須手動寫入 `shared/manual.md`，自動化系統僅作為輔助蒐集。

- **目前觀測**  
  - 從 2026‑11‑17 至 2026‑11‑24 的每日快照皆顯示「本次整理視窗沒有可用 issue」，因此在此期間未產生新的跨 Issue 主題、決策或可辨識的標籤。

## Recent Themes
- **缺乏活躍 Issue**：連續八天的快照皆未偵測到任何可用 Issue，暗示目前 repo 可能處於靜止或維護階段。  
- **等待更新**：所有快照的「Open Loops」皆指向「等待下一輪 issue 更新後再整理」，這是唯一可辨識的近期主題。

> **註**：若未來出現新 Issue，相關主題將在此節更新。

## Constraints
1. **資訊完整性**  
   - 只能引用已在 Issue 或 Comment 中確認的事實；若資訊來源不明或相互矛盾，必須標示為「不確定」或「待確認」。
2. **避免冗餘**  
   - 長期記憶不應直接搬錄每日快照的逐段文字，而是抽象出可重用的規則或事實。
3. **手動維護優先**  
   - `shared/manual.md` 中的手動筆記具有最高優先權，任何自動生成的內容若與之衝突，應以手動筆記為準。
4. **更新頻率**  
   - 只有在 Issue 狀態變更（新增、關閉、標籤變動）時才
