# Repository Memory

## Stable Context
- **資料來源**：所有長期記憶皆以 GitHub Issue / Comment 為原始事實依據，手動維護的 `shared/manual.md` 只作為規則與限制的彙整，不會直接取代 Issue 內容。  
- **手動筆記原則**：  
  - 只保留 **穩定規則、長期決策、常見限制** 以及 **repo 內部慣例**。  
  - 不會完整複製 Issue 原文；若需要引用，僅以摘要或關鍵要點呈現。  
  - `compact‑memory` 工作流程會讀取此檔案，但不會覆寫它。  
- **Issue 整理流程**：每日快照由活躍的 issue agents 產出，若當日無可用 Issue，則保留既有記憶並等待下一輪更新。  
- **跨 Issue 主題偵測**：目前的快照未偵測到任何跨 Issue 主題或決策，表示近期沒有共通議題需要統一處理。  

## Recent Themes
> 近期（過去 30 天）所有每日快照皆顯示「本次整理視窗沒有可用 issue」，因此沒有可辨識的重複或新興主題。  
- **無新議題**：每日皆回報「等待下一輪 issue 更新後再整理」。  
- **無跨 Issue 主題**：`Cross‑Issue Themes` 欄位皆為「目前沒有可辨識的跨 issue 主題」。  

## Constraints
- **手動筆記不可被自動覆寫**：`shared/manual.md` 必須保持人工編輯的狀態，系統不會自動更新此檔。  
- **Issue 為唯一真實來源**：任何事實、決策或待辦必須先在 Issue 中出現，才能被納入長期記憶。  
- **每日快照上限**：每次快照僅檢視最近 30 天內、最多 100 個 Issue；若超出上限，可能會遺漏較舊的資訊。  
- **不確定性**：目前缺乏任何 Issue 資料，導致無法確認是否存在隱藏的長期規則或限制。  

## Open Loops
- **等待 Issue 更新**：所有每日快照皆列出「等待下一輪 issue 更新後再整理」，表示目前沒有待解決的具體 Issue。  
- **潛在新主題**：若未來出現新的 Issue，需重新評估是否形成跨 Issue 主題或需要新增穩定規則。  
- **資訊不足**：因缺乏 Issue 記錄，無法確定是否有尚未被捕捉的
